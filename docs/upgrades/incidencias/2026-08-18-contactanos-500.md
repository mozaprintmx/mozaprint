# 2026-08-18 · Internal Server Error en /contactanos

**Base**: test (`saas~19.3`) · **Estado**: ✓ **resuelto en test y en producción**
**Aplicado en producción**: 2026-08-22, el día que Odoo subió la base a `saas~19.3`
**Severidad si pasara en producción**: **alta** — `/contactanos` es el formulario que
alimenta el CRM (Fase 1). Se pierden leads sin que nadie se entere.

## Síntoma

```
https://mozaprintmx-test-saas19-0818.odoo.com/contactanos
Internal Server Error
```

Una sola página. El resto del sitio está sano, **incluidas las 5,012 fichas de
producto** — en 19.3 no se repite el fallo del salto anterior.

| Ruta | Test (19.3) | Prod (19.2) |
|---|---|---|
| `/`, `/shop`, carrito, `/terms`, y las otras 19 páginas | 200 | 200 |
| `/shop/<producto>` | 200 | 200 |
| `/contactanos` | **500** | 200 |

## Por qué este sí dejó traza (y el de 19.2 no)

Al contrario del [fallo del 2026-08-15](2026-08-15-ficha-producto-500.md), aquí la
página de error **sí es la de Odoo** (6.8 KB en vez de 265 bytes de werkzeug crudo).

Esa diferencia es el diagnóstico: significa que **las vistas combinan bien** y el
fallo ocurre al **renderizar**. Con sesión de administrador sale el traceback
completo:

```
AttributeError: 'website.visitor' object has no attribute '_get_visitor_from_request'
Template: website.contactanos · Reference: 4122
Element: <t t-set="logged_partner"
            t-value="request.env['website.visitor']._get_visitor_from_request().partner_id"/>
```

> Regla que complementa la del incidente anterior: **500 sin página de error de Odoo
> → capa de vistas. 500 CON página de error de Odoo → error de ejecución, y hay
> traceback**. Pídelo con sesión de admin antes de investigar nada más.

## Causa raíz

El método `_get_visitor_from_request()` **se mudó del modelo `website.visitor` al
modelo `ir.http`** en saas~19.3.

Existen dos vistas con ese contenido, por el mecanismo COW del editor del sitio:

| Vista | Qué es | 19.2 | 19.3 |
|---|---|---|---|
| **2335** `website.contactus` | La genérica de Odoo (`website_id=False`) | `env['website.visitor']…` | ✅ migrada a `env['ir.http']…` |
| **4122** `website.contactanos` | **Nuestra copia por-website** | `request.env['website.visitor']…` | ❌ **sin tocar** → 500 |

Odoo migró lo suyo y no miró lo nuestro. **Es exactamente el mismo patrón que las dos
incidencias anteriores**: el riesgo no está en lo que Odoo trae de fábrica ni en
nuestros campos `x_`, sino en **lo que personalizamos encima de algo que Odoo después
reestructura**. La copia existe porque en su día se renombró/tradujo la página desde
el editor.

## Reparación

[`scripts/fix_vista_contactanos.py`](../../../scripts/fix_vista_contactanos.py) —
dry-run por defecto, respaldo en `backups/` y `--rollback`.

```diff
- request.env['website.visitor']._get_visitor_from_request().partner_id
+ request.env['ir.http']._get_visitor_from_request().partner_id
```

```bash
python scripts/fix_vista_contactanos.py --target test            # simulacro
python scripts/fix_vista_contactanos.py --target test --apply
python scripts/fix_vista_contactanos.py --target test --rollback --apply
```

**Verificado el 2026-08-18**: las 24 páginas publicadas en 200 (antes 22 de 24), el
formulario renderiza sus campos (`contact_name`, `email_from`, botón Enviar) y el
auditor sale sin hallazgos. Respaldo en
`backups/vista_contactanos_test_20260818_170020.json`.

Busca **por contenido, no por key**: si otra copia por-website arrastra la misma
llamada, también la repara.

### El guardarraíl, y por qué no es el número de versión

⚠️ Aplicar este fix en 19.2 **rompería** lo que funciona: ahí el método sí vive en
`website.visitor`.

El script no se fía de parsear la versión. Usa **evidencia**: mira las vistas
**genéricas de Odoo** (`website_id=False`), que son la fuente de verdad de dónde vive
el método en esa base. Si Odoo todavía lo llama sobre `website.visitor`, **aborta con
código 1** aunque le pasen `--apply --si-produccion`.

```
✗ ABORTADO. Las plantillas propias de Odoo en esta base todavía llaman al
  método sobre `website.visitor`:
      id=2335 website.contactus
```

Probado contra producción (19.2): aborta. Se descubrió porque la primera versión del
script solo imprimía un aviso y **habría parcheado también la vista genérica de
Odoo** — el control contra producción lo cazó antes de que existiera el riesgo.

Además solo toca **nuestras copias por-website**. Las de Odoo las migra Odoo; si
alguna quedara mal, es bug suyo y se reporta, no se parcha aquí.

## ¿Aplica a producción? — SÍ, y ya se aplicó

**Odoo subió producción a `saas~19.3` el 2026-08-22** y el fallo apareció idéntico:
misma vista 4122, mismo arch, `/contactanos` en 500 mientras el resto del sitio seguía
en 200. Tercer upgrade seguido en que el fix preparado en test se aplica el mismo día sin
sorpresas.

```bash
python scripts/fix_vista_contactanos.py --target prod                      # simulacro
python scripts/fix_vista_contactanos.py --target prod --apply --si-produccion
```

Verificación: **las 26 rutas del barrido en 200**, el formulario renderiza sus campos
(`contact_name`, `email_from`, botón Enviar), el PDF sigue cuadrado en los 4 casos y las
líneas facturables siguen en 0. Respaldo en
`backups/vista_contactanos_prod_20260822_210547.json`.

## Cómo se detecta automáticamente

Aquí estaba el hueco: **ninguna revisión estructural lo ve**. La revisión [1] busca
herencias mal formadas y esta vista está perfectamente formada.

Lo cazó el **barrido HTTP [5]** — y solo porque `/contactanos` estaba en su lista fija
de 5 rutas. Si el fallo hubiera caído en `/nosotros` o en cualquier catálogo, habría
pasado inadvertido hasta que un cliente se topara con él.

**Corregido en el mismo commit**: la revisión [5] ahora barre **todas las
`website.page` publicadas** además de las rutas fijas y 3 fichas de producto reales.
Pasó de 8 rutas a 26 en esta base. Cualquier página que reviente en el futuro sale
sola.

## Lección general

Van **tres incidencias con la misma causa** (ficha de producto, columna de imagen del
PDF, y esta). Cada texto o página personalizada desde el editor del sitio crea una
copia por-website que el upgrade migra peor que el original.

La medida que ataca la causa —y no el síntoma— es **inventariar esas copias y
preguntarse, una por una, si la personalización justifica el riesgo**. Eran 64 en la
base de test anterior.
